BLOCKER — all four confirmed

1. Governance checks are not required in the live ruleset. FACT
Verified via gh api repos/xLZDx/Personal_Decision_Command_Center/rulesets/22899342: a pull_request rule with required_approving_review_count: 0, require_code_owner_review: false, and no required_status_checks rule at all. gh pr view 20 confirmed PR #20 merged 2026‑09‑12 with governance: FAILURE (verify: SUCCESS).
Important reframing. This is not an accidental governance failure or a silent bypass. core/DECISION_LOG.md:139–145 records an explicit operator decision from 2026‑09‑12: required checks were deliberately removed so functional work would not be blocked by G1 process polish; PR #19 merged on that basis with no GPT‑PM APPROVE. The real defect lies elsewhere: core/PLAN_MASTER_GATES.md:11–12 and core/RISK_REGISTER.md were never updated to reflect that decision (G1 is still marked "NOT YET CLOSED", G2 "BLOCKED — needs G1 closure first," even though G2 code (PR #20) has already merged). The audit's recommendation ("restore checks or write an ADR") is broadly right, but the correct fix is to sync the docs with the decision already made, not to reverse it.
2. Provenance fail-open in packages/provenance/src/dag.ts:55–73. FACT
isAiSafe() only checks node.ai_policy === 'DENY', never === 'ALLOW' — at the TypeScript type level there is no third value, but the executable check is not bound to the zod schema (packages/contracts/src/provenance.ts): any object built without going through AiPolicySchema.parse(), carrying an arbitrary ai_policy (including undefined), passes as safe as long as it has no ancestors. provenance.ts:9's own comment says as much: "a type that carries an ai_policy field does not by itself stop anyone from serializing it" — the actual enforcement point (dag.ts) is exactly where the audit found the gap. An ALLOW node with empty provenance: [] is indeed accepted as a valid root purely by comment-level convention, with no type-level or runtime distinction between "a genuine source leaf" and "an accidentally empty array."
3. D1 schema permits Telegram + ALLOW. FACT
In infra/migrations/0001_ingest_outbox.sql:57–63, source_policies has independent CHECKs on source IN ('telegram','gmail') and ai_policy IN ('ALLOW','DENY'), but no composite constraint forbidding the pair telegram + ALLOW. In ingest_events (:79–91) the source column, the FK to source_accounts, and the FK to source_policies are three independent columns with no consistency check between them. Confirmed structurally by direct schema reading (no composite FK/CHECK exists); the audit's empirical SQLite probe was not re-run, but that was unnecessary — the gap is visible in the DDL itself.
4. Reconciler/outbox: incoherent state-machine query. FACT — already known to the project
Not a new finding: the project itself found and documented the same defect the same day, independently of the external audit — see core/DECISION_LOG.md:8–31 and governance/plans/G2_PIPELINE_ARCHITECTURE_PROPOSAL.md:9–34 (4 agents, all independently converging). Read directly: docs/architecture/TDD.md:840–846 writes the query over ingest_events.state, while next_attempt_at/attempt_count live only on processing_outbox (:129–138), and the only index (idx_processing_outbox_reconciler, :142) is built on an incompatible state domain. Also independently confirmed: the attempt-cap-invisibility bug — attempt_count < MAX_PROCESSING_ATTEMPTS as a WHERE filter excludes an event exactly at its attempt cap from ever transitioning to DLQ (TDD.md:845, ADR-006:43). Nothing implemented — awaiting a GPT‑PM ruling.
