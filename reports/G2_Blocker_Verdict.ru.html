Вердикт GPT-PM по архитектуре G2

Полный текст сохранён в core/DECISION_LOG.md и в статусе governance/plans/G2_PIPELINE_ARCHITECTURE_PROPOSAL.md. Ниже — разбор по пунктам.

Blocker§2 · схема реконсилятора

Отклонена «чистая» схема на базе processing_outbox

Предложение агента architect (состояния DONE/TERMINAL только в processing_outbox) нарушает собственное разделение ADR-006: истина по обработке — в ingest_events.state, истина по транспорту — отдельно в processing_outbox.state. Схема не выдерживает случая, когда событие уже стало терминальным, а строка outbox всё ещё DISPATCHED.

Требуется: предикат отбора должен по-прежнему смотреть на ingest_events.state через join с просроченной строкой outbox; индекс — доказанно покрывающий (EXPLAIN QUERY PLAN + нагрузочный тест). Транспортное терминальное состояние допустимо как оптимизация, но не как единственный источник корректности.
Blocker§3 · лимит попыток

Отклонён способ перевода в DLQ

Безусловный захват строки с последующим разбором на «дошло / не дошло» — не то, что требует спецификация: переход в DLQ должен происходить одной атомарной транзакцией вместе с той самой неудачной попыткой обработки, а не отдельным проходом реконсилятора, который «обнаруживает» уже исчерпанный лимит.

Требуется: транзакция, доводящая attempt_count до MAX_PROCESSING_ATTEMPTS, сама же атомарно ставит DLQ и создаёт строку dead_letter_events. Отдельно: истечение видимости в очереди не должно расходовать бюджет попыток обработки.
Blockerновая находка

Восстановление зависших PROCESSING-событий не специфицировано

Состояние PROCESSING есть в модели событий, но реконсилятор, как он описан, выбирает только ACCEPTED/RETRYABLE_FAILED. Если обработчик упал между PROCESSING и следующим переходом — событие навсегда невидимо для реконсилятора. Ни один из четырёх агентов и сам аудит это не заметили.

Требуется: ограниченная по времени аренда/claim с TTL и compare-and-swap (или эквивалент), совместимая с повторной доставкой очереди и не нарушающая идемпотентность записи в домен.
Подтверждено§4 · services/resolver

Откладывание candidate-resolution в G5 — верно

PLAN_MASTER_GATES.md относит распознавание Identity/Project/Stream/Topic к G5. G2 вправе построить переиспользуемые примитивы запросов/квот и интерфейс к резолверу, но не реализовывать сам выбор кандидатов внутри services/processor.

Major§5 · таблица devices

Убрать таблицу devices из миграции 0001

Сама миграция декларирует правило «не создавать схему под будущий гейт заранее», но тут же его нарушает ради G7. Обоснованной зависимости G2 на эту таблицу нет.

Требуется: удалить из 0001_ingest_outbox.sql; G7 заводит таблицу в собственной миграции.
Решение§5 · provenance DAG

Многошаговый обход — сейчас в памяти, персистентный DAG — позже

G2 обязан реализовать и протестировать общий транзитивный обход происхождения (это уже требует ADR-005), но не обязан заводить персистентные таблицы предков для доменных сущностей G5/G6. provenance_event_id должен ссылаться прямо на ingest_events(event_id).

Подтверждено, усилено§7 · provenance fail-open

Дыра в isAiSafe() реальна — но чинить нужно шире

Мало заменить !== 'DENY' на === 'ALLOW'. Нужны различимые схемы узлов (source-event / static-config / derived), чтобы произвольный производный объект не мог стать доверенным корнем только за счёт пустого provenance: []; политика в sourceEventNode() должна приходить из проверенного пути, а не от вызывающего кода напрямую.

Major§7 · telegram + ALLOW

Нужна структурная защита, не только CHECK

Помимо запрета telegram + ALLOW в source_policies, нужны составные внешние ключи, связывающие source у события с source у аккаунта и у политики — только на уровне приложения этого недостаточно.

Major§7 · коллизия идемпотентности

Нужно менять контракт и миграцию, не только функцию ключа

TDD уже называет четвёртое поле ключа — source_version_if_needed — которого нет в реализации. GPT-PM подтвердил находку и добавил независимое доказательство от Telegram (в TDLib message_id стабилен, edit_date меняется при правке).

Требуется: добавить поле версии в нормализованный контракт события и в D1-схему, использовать его в идемпотентности для версионируемых событий.
Majorновая находка

ProvenanceValueSchema не соответствует TDD

Замороженная спецификация описывает ProvenanceValue<T> с полями sensitivity, created_at, derivation_version для строк/чисел/дат/булевых/enum/агрегатов; текущая общая схема жёстко требует непустую строку и эти поля не хранит.

Требуется: либо обобщённая/дискриминированная реализация под все случаи TDD, либо явное официальное исправление самой спецификации.

Принято без возражений

  • Атомарный upsert счётчика бюджета одной инструкцией.
  • Жёсткий предел MAX_ROUTING_HINTS — значение 16 считать предварительным до измерения на квота-стенде.
  • Замер CPU внутри Worker через Date.now() недопустим как доказательство.
