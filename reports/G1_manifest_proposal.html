01

What was actually built

governance/plans/G1_MANIFEST_PROPOSAL.yaml — an implementer-authored draft of the gate manifest. It lives in plans/ rather than gate-manifests/, and that is not a filing convention: a manifest an implementer can freely edit in their own branch has no authority at all (INV-28). The file carries the markers NON_BINDING_PROPOSAL, IMPLEMENTER_AUTHORED, HAS_NO_AUTHORITY and the header comment GPT-PM dictated.

24 allowed_paths, 4 forbidden_paths, no bare ** anywhere. Every entry is tagged with where it comes from: [CUMULATIVE] — already in the branch's diff, [REMAINING] — needed by a named remaining closure action, [BOTH] — both.

Why cumulative rather than "only what is left". The guard evaluates git diff BASE_SHA...HEAD_SHA, so it checks the whole PR merge range, not the last commit. A manifest listing only future actions would fail on paths the branch already carries — at the exact moment it was adopted. This is GPT-PM correcting its own earlier instruction, and the correction is right.

Validated by the same code CI executes

The check imports parsePathList, compilePattern and checkScope directly from scripts/verify/check-gate-scope.mjs rather than restating them in a more forgiving copy written for the occasion. A defect in the real guard has to surface here instead of hiding.

02

The finding that matters more than the manifest

The approval hash is not out of the implementer's reach

The entire manifest-integrity mechanism is built on the approved hash living outside the implementer's reach. GATE_MANIFEST_INTEGRITY.md says so; so did the proposal. It does not.

Measured after the operator authenticated gh: a classic PAT for the xLZDx account with repo, workflow, admin:org, admin:repo_hook, admin:enterprise and more; .permissions on this repository is {"admin":true,…}. The same session that authors a manifest can:

  • set GATE_MANIFEST_APPROVED_HASH_G1;
  • adopt a manifest and then set the hash to match it — precisely the self-authorizing loop NM3 identified and this mechanism exists to prevent;
  • remove or weaken branch protection;
  • edit the Governance workflow that polices it;
  • merge its own pull request.

None of that will be done. The point is that none of it is prevented. Every control described here as operator-held is, as of now, procedural — it rests on the implementer not doing what it is fully able to do.

The token is classic rather than fine-grained, so it has no per-repository boundary: the same holds for every other repository the account can reach. That is beyond G1's scope, but it is the operator's to know.

Three ways to restore the mechanical property — the choice is the operator's

None of these is the implementer's to pick.
OptionWhat it givesWhat it costs
Fine-grained token scoped to this repository No administration, no variables/secrets write. The hash is unreachable again; contents and pull_requests remain Administrative operations become manual
Keep the broad token out of the agent's environment The same guarantee without reissuing anything Every admin step is done by hand
Accept the procedural model explicitly No access changes at all The documents must stop calling these controls mechanical

The third option is what the repository's documents are effectively doing today without admitting it. The first two are what they describe.

An earlier session had recorded that /branches/main/protection answers Branch not protected. An unauthenticated probe returned HTTP 401, so it was written up as unreproducible and withdrawn. A failed measurement is evidence about the measurement first. The conclusion never moved, only the reason under it — which is what made the mistake comfortable enough to write down.

06

What is now the operator's

Six decisions, none of them the implementer's

  1. Read and edit the proposal. Narrowing it is always safe; widening it is the thing to be suspicious of.
  2. Write the result to governance/gate-manifests/g1.yaml, replacing the header and the status block with adoption markers. As its own commit on main, not inside the gate PR: that path is in forbidden_paths, so a PR carrying it must fail — correctly.
  3. Compute the sha256 of the adopted file: Get-FileHash -Algorithm SHA256 governance\gate-manifests\g1.yaml.
  4. Set that value as the repository variable GATE_MANIFEST_APPROVED_HASH_G1.
  5. Decide and apply branch protection — the single-account configuration is in §6 of the evidence artifact: PR required, both checks required, approving reviews 0, Code Owner review off (otherwise the self-approval deadlock), applied to administrators, force-push and deletion disabled.
  6. Decide the credential model from §02. A fine-grained token, a hand-operated admin path, or an explicit acceptance of the procedural model. Whichever is chosen, the documents must end up saying exactly what the token actually permits.

The PR can now technically be opened from here — gh is installed and authenticated. It has not been: the approved plan ends at a stop, and opening the PR is step 6 of GPT-PM's sequence and needs its own GO. Say the word and it will be requested.

07

The prediction this is willing to be wrong about

Stated before the run, so the outcome is evidence either way. When the pull request is opened:

  • CI should pass. Locally 88 tests are green and all 30 mutations are killed. A failure here would mean the workflow is wrong, not the code.
  • Governance should FAIL, at the manifest step. No adopted manifest exists and the variable is unset. That failure is the evidence: the first observation of the guard refusing anything.
  • If Governance passes, the check is broken and G1 cannot close on it.

A control never observed refusing anything is not known to work.

G1 is not closed. G2 does not begin. The manifest proposal stays a proposal until the operator adopts it and sets the hash; every piece of evidence this project has as of now is local.
