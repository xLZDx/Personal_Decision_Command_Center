§ 1

The defect: an ungated-PR manifest could never reach main by any route

Before this fix, governance.yml required every PR to declare a gate — otherwise step 4 failed unconditionally. While direct pushes to main were still possible, this did not matter. But this same session added branch protection requiring a PR and a green governance check — and the PR carrying G0's own evidence (the CPU probe itself) stopped being mergeable at all, because it belongs to no gate.

The first design — add Gate: NONE, read against a fixed governance/gate-manifests/_floor.yaml — turned out to be structurally unmergeable. INV-28 forbids any gate-labeled PR from touching governance/gate-manifests/**: a diff cannot be validated against a manifest that same diff could have just rewritten. The _floor.yaml file, living in that same directory, forbade the identical thing of itself.

Both introduction paths rejected it the same way: a Gate: G1 PR would fail under g1.yaml's own rule; an ungated PR would fail under the new file's own rule, applied to itself in the same check. No PR — gated or not — could physically land this file on main.

Found by tracing both check paths, not by inspection alone; the rule was already written and sitting in the working tree before the conflict became apparent.

§ 2

The fix: code instead of a manifest file

The floor's rules moved out of a YAML file under governance/gate-manifests/ into a plain .mjs module, scripts/verify/check-floor-scope.mjs — a path G1's own manifest already allows (scripts/verify/*.mjs). As ordinary code it is protected exactly like governance.yml itself: changeable by whichever gate's manifest permits editing scripts/verify/**, no more and no less. The forbidden list (governance/gate-manifests/**, approval records, the frozen TDD, the workflow and CODEOWNERS themselves) did not change at all — only the rule's address and the ceremony for editing it did.

The function reuses checkScope/changedPathsFrom from check-gate-scope.mjs — one audited path-matching engine, not two.

§ 3

Side finding: CRLF + import.meta.url breaks vitest locally

The local suite occasionally failed with a SyntaxError pointing at an unrelated file's import line. Root cause, confirmed by bisection: check-gate-scope.mjs contains one import.meta.url reference, and Vite's SSR transform corrupts the load when the file's line endings are CRLF. This machine's global core.autocrlf=true rewrites the working copy to CRLF on ordinary git operations (checkout, stash), even though the committed blob is — and always was — LF (git cat-file -p HEAD:… — 0 CRLF pairs). No repository content changed to work around it: the working copy was simply re-normalized to match what was already committed.

§ 5

Merge authority: two rounds with GPT-PM, not on the operator's word

Verified directly, not accepted as reported

The operator reported that GPT-PM said it has full rights to merge. Before acting on that, two direct questions went to GPT-PM itself, in the same conversation, rather than trusting the paraphrase.

Round 1 — does APPROVE lift INV-20's requirement

Yes, for this project: explicit operator delegation + GPT-PM's APPROVE on the exact final head + green required checks. With a mandatory carve-out — a PR that itself changes governance/gate-manifests/**, approval records, or branch-protection/ruleset settings gets no auto-merge even with a clean APPROVE: that needs the operator's own separate authorization. A .github/workflows/** content change is covered if it was part of the approved diff — exactly PR #3's case.

Round 2 — can GPT-PM itself merge, as a genuinely separate actor

No real actor separation exists. GPT-PM technically holds GitHub write access (merge_pull_request, review) through its connector — but that connector authenticates as the same xLZDx account Claude's own gh uses. To GitHub, "GPT-PM merges" and "Claude merges" are the same actor; a review GPT-PM submits from that connector could itself be rejected as self-approval. Same root cause as R13.

The operator was told this plainly, with no smoothing over. The adopted design: Claude performs the mechanical merge as the executor of GPT-PM's verified decision — a logical separation of decision-maker from implementer, not a GitHub-account-level one.

§ 6

Recorded as a rule — globally and in this project

The operator explicitly confirmed scope — not one project, all of them: ~/.claude/CLAUDE.md §24 (new section). Conditions: a fresh APPROVE naming the current head; the head unchanged since that APPROVE; every required check green on that same head; the PR mergeable; the ordinary merge method, no bypass/force/disabled checks; the PR not touching an authority-surface path (manifests, approval records, CODEOWNERS, protection settings) — that class still needs the operator's own separate authorization. The bar is VERDICT: APPROVE specifically, never "roughly approved" or a paraphrase of one.

For this project, the same rule is recorded in core/DECISION_LOG.md naming exactly which paths here count as an authority surface: governance/gate-manifests/**, governance/operator-approvals/**, .github/CODEOWNERS, ruleset settings. The global file is the source of the rule; the decision log is how it applies here specifically.
