§ 2

The defect being fixed

governance/GATE_MANIFEST_INTEGRITY.md promised that the scope check runs only after the manifest hash check, in the same job. The code did not deliver that. There were two independent workflows with needs: [], and nothing sequenced them.

Worse, gate-scope.yml's own header comment asserted that it ran after the integrity check. The code read as correct. This is exactly the NM3 circularity the mechanism was written to close: a diff validated against a document the same diff could have rewritten.

It is now one workflow, .github/workflows/governance.yml, three steps of one job: resolve the gate → verify the manifest's sha256 against the repository variable → check the changed paths. The third step reads the manifest path from the second step's output, and that output is only written after the hash comparison succeeds — so on a hash mismatch the scope step is unreachable.

§ 3

Five defects found along the way

None of them were in GPT-PM's findings

01

* crossed /

The old check matched with bash [[ "$path" == $pattern ]], where * passes straight through the separator. An entry allowed_paths: [packages/*] silently authorized packages/anything/deep/file.ts.

A manifest a human reads as "the top level of packages" in fact authorized the whole subtree. That is an error in the direction of permitting — the worst direction for a check whose entire job is to refuse.

02

The reader truncated a list silently

The first version of my own new reader ended a block at any non-indented line. A list item that lost its indent took the same branch, and parsePathList returned an empty list with no error at all.

For forbidden_paths that is zero enforcement, and it is invisible: an empty list is exactly what a manifest declaring no forbidden paths produces. The file still reads correctly to a human, so your hash approval would have been given to a document that enforced nothing. Found by internal security review before commit.

03

run() had no coverage at all

The only function CI actually executes, and the one whose exit code is the control. A regression dropping the violation branch would have left every unit test green while the script exited 0 on a real scope violation.

It is now an exported function returning an exit code, with injected dependencies, and every exit path is asserted — including an unreadable manifest and a failed git diff, which previously would have looked like "no changes".

04

changedPathsFrom() had no coverage at all

Including the -z handling the function exists for: without it git quotes and escapes unusual filenames, and an escaped path would be matched against patterns written in terms of the real one.

It is now tested against a real temporary git repository, with filenames containing a space and non-ASCII characters. The test passes on Windows, which means -z genuinely does what the comment claims rather than what I assumed.

05

A mutation's label claimed more than it proved

The mutation "run past the end of the block into the next key" was reported killed — but what killed it was a parse error, not the silent list-widening its name implied.

This is precisely the defect class this repository exists to catch: a claim broader than its check. The label is rewritten, and two mutations that do demonstrate the real hazard replace it.

§ 5

What the internal review produced

Three read-only specialists (security, test quality, integration) read the change before the GPT-PM round — a sequencing requirement, not a suggestion. They found more real defects than the external round, which is expected: they had file access.

The most uncomfortable finding was my own sentence. I had written in the design document that "the matcher and reader are mutation-tested". Of those two functions it was true. Of the file it was not: the part CI executes had no coverage of any kind. The document now enumerates what is covered instead of summarising it in one phrase. This is a recurring defect class in this repository — a claim broader than its check — and it showed up in the very artifact built to catch it.

Two smaller ones: the & (YAML anchor) rejection branch and the block-scalar rejection branch had no assertion at all — either could have been deleted outright and the suite would have stayed green. Both are now covered, each by its own mutation.

§ 7

Limits of the mechanism

Documented in the design file, not fixed in this change

  • Gate Which gate a PR claims to be comes from the branch name or the PR body, both implementer-controlled. Once several gates have approved manifests, the check will prove "this diff fits some approved manifest", not "it fits the manifest of the gate genuinely in progress". Closing that needs the gate binding to come from operator-controlled state.
  • Plan The manifest's own plan_id and plan_hash are verified against nothing. The hash check proves the manifest file is byte-identical to what you approved — not that it points at a current plan.
  • CI A PR editing .github/** or scripts/verify/** runs with the modified content: CI cannot police its own definition. Both directories are CODEOWNERS-protected for that reason — and it is why merge authority, not CI, is the control that actually enforces.
  • Pattern The allow-everything warning fires only on the literal entry **. The near-equivalent **/* is not flagged. An implementer cannot introduce one — the manifest's content is fixed before any diff is evaluated against it — but it is a gap in the operator-facing warning.
